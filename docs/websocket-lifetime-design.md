所属: [Std拡張WebSocket開発](./README.md)。問題定義・設計根拠の詳細資料。

2026-11-02作成。状態は**設計案**。ここに記す保証は現在の実装が満たすと確認された
性質ではなく、これから実装・検証する目標である。初稿ではコードを変更しなかった。
後続の[純粋モデル試作](websocket-prototype-results.md)で局所補題とテストを検証したが、
実Transport接続・設計全体の証明は未完了である。

## 1. 問題定義

当初は「close後にデータフレームが出る競合」を低リスクと評価したが、
「相手が無視するだけで無害」という判断には根拠が不足していた。
重要なのはRFC適合性に加え、**誰が接続を操作でき、その権利がいつ失効し、
処理中のI/Oが使う資源をいつ解放できるか**という寿命管理の契約である。

原因をStdのHTTP設計の欠陥と断定しない。HTTPループ内で管理していた接続を
upgrade後に複数タスクから操作できるようにしたことで、拡張側が新しい並行性と
寿命管理の責任を引き受けた、と捉える。

### 現在確認できる事実

- [sendDataFrame](../StdExt/Http/WebSocket/Connection.lean) は `closeSent` の確認と
  送信を別操作として行う。確認後に別タスクがCloseを送り、その後データが送られる
  順序を排除できない。ピアのCloseへの自動応答とも競合し得る。
- `sendCloseOnce` のフラグ更新は原子的だが、他の送信との直列化はしない。
  フラグはCloseの送信完了を意味せず、送信失敗時も単独では結果を表せない。
- `WebSocket.close` はフレーム送信であって、オブジェクト解放でもTCP切断でもない。
- [Upgraded.ofTransport](../StdExt/Http/Server/Upgrade.lean) の送受信クロージャは
  socketへの参照を保持する。参照の生存と、接続を操作してよい期間は同一ではない。
- [performUpgrade](../StdExt/Http/Server/Connection.lean) は継続自身を待つが、
  継続がWebSocketを渡した独立タスクすべてを追跡・joinする仕組みではない。
- Lean 4.35.0の `Transport.close` は既定で何もしない。標準のTCPインスタンスは
  これを上書きせず、FD解放をfinalizerに委ねる。したがって、現在の
  `Transport.close` 呼び出しだけでは、即時切断や受信待ち解除を保証できない。

### 未確認事項

非同期native I/O完了までのsocket・バッファ保持、finalizerとの競合、
FD再利用への対処は、native実装まで確認する必要がある。
当初はローカルツールチェーンに該当nativeソースがなく未確認だった。
後続の[依存先契約調査](websocket-dependency-contracts.md)で対応版の公開ソースを取得し、
送信中のsocket・バッファ保持、受信中の参照保持、finalizerのclose callbackでの解放を
確認した。実行環境のlibuv版も1.48.0と測定した。ただしnative全体の形式検証や、
全異常経路・FD再利用・実行バイナリとの完全な対応の検証は未実施である。
**メモリ破壊・別接続への誤送信・不正読み出しは実証されていないが、
Lean側の参照保持だけでnative境界まで安全と断定もしない。**

## 2. 分けて定義する保証

| 層 | 目標 | 証明・検証の範囲 |
|---|---|---|
| プロトコル | Close送信後にデータフレームを出力しない | 純粋な遷移と出力列の不変条件 |
| 並行操作 | sendとcloseの順序が明確で、失効後の要求はI/Oを開始しない | 要求受理点、実行器の直列化、結果通知 |
| 終了 | 終了完了時に管理対象タスク・保留I/O・未解決要求が残らない | キャンセル、完了待機、Transport契約 |
| native資源 | 処理中のI/Oが使う資源を早期解放しない | native実装の検証、または明記した仮定 |

「Close要求を受けた」「Closeを書き始めた」「書き込みが完了した」
「接続の終了が完了した」を区別する。送信成功も相手の受信・アプリ処理完了の証明ではない。
shutdownで要求の受理を止めることと、物理的な資源解放も区別する。

### HTTP/2とも自然な対応関係を保つ

**HTTP/2が入っても矛盾せず、自然な対応関係が取れることを設計方針とする。**
これは今回HTTP/2対応を実装するという意味ではない。証明対象や終了APIを、
「一つのWebSocketが一つのTCP接続を排他的に所有する」という仮定に固定しない。

| 層・操作 | HTTP/1.1 WebSocket | HTTP/2 WebSocket（RFC 8441） |
|---|---|---|
| 確立 | 101でHTTPから接続を移譲 | Extended CONNECTで一つのストリームを確立 |
| WebSocketの終了手順 | Closeフレームの交換 | 同じくCloseフレームの交換 |
| 下位の送信方向の終了 | TCPのwrite側shutdown等。実際に提供される能力を確認する | 当該ストリームのEND_STREAM |
| 下位の異常中断 | 接続を中断する能力が必要。現行の標準TCP Transportには不足 | 当該ストリームのRST_STREAM |
| 下位資源の共有 | upgrade後のTCP接続は通常そのWebSocket専用 | 同じHTTP/2接続を他ストリームと共有 |
| 完了待機 | WebSocket終了、保留I/O静止、TCP解放完了を区別 | WebSocket終了、ストリーム終了、共有接続の終了を区別 |

これらは役割の対応であり、CloseフレームとEND_STREAM、TCP shutdownとRST_STREAMを
同じ操作と見なすものではない。下位のEOF・resetだけでWebSocketの正常なclosing
handshakeが成立したとはしない。

依存する `http2-lean` の `ExtendedConnect.Tunnel` は `send`、`recv?`、
`closeSend`、`cancel`、`wait` を分けている。参考になるが、このAPI名だけから
native資源の解放完了や有界時間内の終了まで保証されると解釈しない。

接続所有タスク案の「接続」は、WebSocketの論理セッションを意味する。
HTTP/2ではWebSocket側がストリーム上の要求を順序付け、HTTP/2接続側の所有タスクが
多重化・フロー制御・物理socketを管理する。二層の所有関係は矛盾しない。
一つのWebSocketの中断で、他ストリームを巻き込んで共有TCP接続を閉じない。
逆に接続全体の障害は、影響するストリームへ終端イベントとして伝播させる。
GOAWAYも、既存の全WebSocketが直ちに正常終了したという通知ではない。

証明は、共通のWebSocket状態機械と、backendごとの契約への対応に分ける。
HTTP/2ではさらに、接続・ストリームのフロー制御による送信待ち、中断・失効の伝播、
他ストリームへの影響範囲を確認する。単一所有タスクでも送信完了を無期限に待てば
中断処理を止め得るため、保留I/Oの追跡とイベント多重化の要件は維持する。
HTTP/2ストリームの終了定理から、共有TCP資源の解放までを結論しない。

## 3. 設計の第一候補: 接続を単一の所有タスクが駆動する

```text
アプリの送信要求 ─┐
close要求 ───────┼→ 有界の要求受付 → 接続所有タスク → Transport
shutdown通知 ────┘                    ↑ I/O完了・受信イベント
```

- 外部にはsocketや送受信クロージャではなく、要求を送るハンドルを渡す。
  ハンドルが終了後も残ることは許容し、操作権は失効させる。
- 接続状態、送信順序、Transportへの操作開始を所有タスクに集約する。
  受信待ちでsendやshutdownが止まらないよう、イベントを多重化する。
- 書き込み中もshutdownを扱う必要がある。非同期操作を開始して完了イベントを追跡する等、
  保留I/Oをモデルに含める。単なる逐次的なブロッキングループにはしない。
- 要求キューには上限と背圧を設け、飽和時にもshutdownが進められる経路を確保する。
  終了後の要求は明示的な失敗とし、待機者を残さない。
- 利用者が起動した任意のタスクまで強制的に回収できるとはしない。
  接続関連の子タスクはスコープ内で管理し、外へ逃げたハンドルは失効により隔離する。

これは候補であり採用済みではない。ロック方式も比較対象とする。
ただし、全送信の排他制御だけでは、ハンドル失効・受信解除・子タスク回収・native寿命の
問題は解決しない。actor方式も、キャンセル不能なI/Oを自動的に安全にするものではない。

## 4. 契約として先に決めること

| 論点 | 提案・判断の方向 | 未決定の詳細 |
|---|---|---|
| sendとcloseの競合 | 要求受理に一貫した順序を付ける | close以前に受理した未着手sendを送るか、取り消すか |
| 実行中send | Closeをデータフレームの途中に割り込ませない | 完了待ちの上限、異常終了時の部分送信の扱い |
| close API | 開始と終了完了を区別して観測可能にする | 現行APIとの互換性、結果型と待機API |
| ピアClose・エラー・EOF | ローカルcloseと同じ状態機械へ入力する | キュー排出方針、送信失敗とclose理由の優先順位 |
| サーバーshutdown | 新規要求停止、保留操作の解決、終了待機を行う | 猶予期間と強制中断に必要なTransport能力 |
| 重複close | Closeの重複送出を防ぎ、終了結果を共有する | 最初のclose理由を採用するか等の規則 |
| ping・自動pong | データと同じ送信順序管理を通す | 各終了段階で許す制御フレームの範囲 |

これらは証明器が選ぶ方針ではない。実装前に利用者の期待とRFC要件を突き合わせ、
選んだ意味論を文書・型・テストで一致させる。

## 5. Leanでのモデル化と証明対象

純粋な `step : State → Event → State × List Effect` 相当のモデルを作る。
名前や型は未確定。Stateには接続段階に加え、Closeの送信状況、実行中I/O、
受理済み要求と結果を含める。Effectは送信開始・I/O中断・結果通知等を表し、
実行器からI/O成功・失敗・キャンセル完了をEventとして戻す。

証明候補:

1. 到達可能な状態は定義した不変条件を満たす。
2. 終了完了から開状態へ戻らず、新規I/O開始Effectを出さない。
3. Closeの送信開始以後、データフレーム送信開始Effectを出さない。
   既に実行中のデータ送信も追跡し、同一接続への書き込みを重ねない。
4. Closeを二重に送出しない。
5. 各受理要求に対する結果通知は高々一度で、終了完了状態には未解決要求がない。
6. 資源解放Effectは、その資源を使う保留I/Oがなくなった後にのみ出る。

「受理要求がいつか完了する」「shutdownがいつか終わる」は進行性の性質である。
相手の応答、タイマーの発火、スケジューリングの公平性、Transportの中断・完了通知などの
仮定が必要で、安全性の不変条件からは導けない。仮定とタイムアウトの役割を明記する。

### 型だけで共有参照を失効させられるとは限らない

`WebSocket Open → WebSocket Closed` のような型状態は内部遷移の記述には有用だが、
別タスクに残った古いOpen参照を自動的には無効化しない。
Leanに一般的な線形所有権の強制があることを前提にせず、
共有ハンドルの失効は実行時の状態管理と結び付ける。

### 証明と実行系を分離したままにしない

実行器は証明した `step` 自体を使う。出力したEffectの順序、I/O成功・失敗の通知、
要求受付と終了の競合処理についても、モデルとの対応を検証する。
純粋モデルが正しくても、実行器が別経路からTransportを呼べば保証は成立しない。
native呼び出しは明確な境界に閉じ込め、信頼する仕様を列挙する。

## 6. Transportに求める契約と検証

先に[依存先契約の台帳](websocket-dependency-contracts.md)のC1〜C7とA1〜A8を参照する。
特に `Client.shutdown` はwrite側の半閉鎖、`uv_cancel` はTCP writeの汎用中断ではない。
タイムアウトを設けたことだけで、保留I/Oの完了・解放可能性を仮定しない。

現在の `Transport.close` を強制中断と同一視せず、以下の能力が必要かを検討する:

- 新しいI/O開始を禁止する操作権の失効。
- 待機中のrecv・sendを解除できる中断操作と、その完了通知。
- 中断と資源解放の区別、処理中バッファ・socketの保持。
- 重複中断・解放、I/O失敗、EOF、finalizerとの整合性。

これらをStd全体のTransport変更とするか、upgrade向けの追加能力とするかは未決定。
全トランスポートが同じ強制切断能力を持つと仮定しない。
対応能力がなければ、終了保証の不足を明示し、成功したように扱わない。

## 7. 段階的な進め方と完了条件

1. 上記の契約・未決定事項を合意し、現在の保証不足を利用ガイドへ明示する。
2. 純粋な遷移モデルと不変条件の証明を作る。保証する定理を `sorry` や
   根拠のない公理で埋めず、外部仮定は区別する。
3. 制御可能なモックTransportで、send確認後のclose、ピアCloseとの競合、
   shutdown中の受信・送信待ち、重複close、送信失敗、逃げたハンドルの利用、
   キュー飽和を決定的に再現する。偶然のタイミングやsleepに依存させない。
4. 実行器をモデルへ接続し、全I/O経路と要求の結果通知を検査する。
5. 対応するnativeソースを確認し、保留I/Oとfinalizerの競合を必要に応じ
   sanitizer等でも検証する。動的テストを一般的な安全性証明と混同しない。
6. 既存の `lake test` とWebSocket統合テストを実行し、終了契約のテストを追加する。

完了条件は、証明対象・外部仮定・未保証範囲が明示され、実行コードが証明済みモデルを
使用し、競合と終了のテストが通り、native資源の契約について検証根拠が揃うこと。
プロトコルの順序だけを直して寿命問題全体を「解決済み」としない。

## 8. 調査の充足性と定理設定のレビュー

2026-11-02時点の総合判断: **設計候補と条件付きの安全性定理を具体化する情報は
揃ったが、公開API・実行系・終了保証を確定するには不足がある。**
不足の中心は追加の一般調査ではなく、意味論の選択と、限定したbackend契約の検証である。
以下はレビュー結果と提案であり、未決定事項を採用済みと扱わない。

### 8.1 何を始められ、何をまだ主張できないか

| 対象 | 判断 | 理由・着手条件 |
|---|---|---|
| 責務と層の設計 | 着手可能 | Std.Httpの単一ドライバーと、HTTP/2のストリーム所有を対応付けられる |
| 純粋な状態・イベント・Effectの型案 | 着手可能 | 外部I/Oの完了を別イベントにする必要性と、主要な異常系が分かっている |
| close順序・失効の安全性定理 | 条件付きで着手可能 | 受付／実行開始の境界と、既に受けた要求の扱いを先に選ぶ |
| 公開API・実行方式の確定 | 保留 | 結果通知、背圧、待機キャンセル、実行器の失敗処理が未確定 |
| HTTP/1実行器での終了完了保証 | 保留 | pending recv/writeを静止させる能力と、その完了確認が不足 |
| HTTP/2との抽象的な対応 | 着手可能 | セッションと共有接続を分離して記述できる |
| HTTP/2 backendの適合証明 | 保留 | Tunnelの宣言だけでなく、実装の中断・待機・キュー処理の確認が必要 |
| native全体のメモリ安全性・情報漏洩不在 | 主張不可 | RC、FFI、libuv等の部分的レビューは全体証明ではない |
| 無条件・有界時間内の全資源回収 | 主張不可 | 中断能力と進行性の根拠が足りず、タイムアウトだけでは補えない |

### 8.2 定理を書き始める前に埋めるべき意味論

1. **受付と実行開始の区別**: 呼び出し、キュー投入、所有タスクによる受理、
   Effect生成、backendへの登録、完了通知を区別する。
   「close後は送れない」のcloseがどの点かを固定する。
   例として、close受理後は新規sendを拒否しても、以前に受理したsendを排出する契約なら、
   「close受理後にデータ送信開始なし」は成立しない。Closeフレーム開始後の禁止とは別である。
2. **二軸以上の終了状態**: 操作権失効、WebSocketのClose送受信、下位の送受信半閉鎖、
   保留I/Oの静止、所有資源の解放を単一のClosedに潰さない。
   HTTP/2のストリーム終了時には共有TCPが生存してよい。
3. **Effectの実行規則**: モデルが生成したがまだ実行していないsend Effectも追跡する。
   abort後に古いEffectを実行しないこと、開始済みI/Oには実際の完了が来るまで保持を
   続けることを定義する。モデルを呼ぶだけでは実行順の対応は保証されない。
4. **遅延完了イベント**: operation IDと対象セッション等で完了を対応付け、
   古い完了・二重通知が新しい操作を完了させたり状態を再開させたりしないようにする。
   IDを再利用しない規則、または世代の区別が必要かを決める。
5. **要求結果とI/O結果の分離**: 利用者へのキャンセル結果を先に返しても、
   native I/Oが止まったとはしない。待機者が消えた場合やキューが閉じた場合も、
   資源保持と完了回収は実行器が引き受ける。send失敗時の部分送信を正常成功にしない。
6. **所有タスク自体の失敗**: 例外、Effect開始の即時失敗、結果通知失敗、
   キャンセル中の再入で未解決要求を残さない契約を決める。
   自動pong、エラーClose、継続終了時のcloseも同じ経路に通す。
7. **背圧と制御経路**: キューの件数だけでなく保持バイト数・実行中データも数える。
   上限でshutdownが投入できない設計を避ける。HTTP/2のflow-control待ちも
   所有タスクを停止させないことが必要。

ここまでを具体化しないと、状態遷移だけでは正しくても、実装が選ぶ受付順や
実行器の未処理Effectにより実際の保証とずれる。

### 8.3 最初の定理群と適用限界

| ID | 定理の候補 | 前提・適用限界 |
|---|---|---|
| S1 | 初期状態で不変条件が成立し、許された各遷移が保存する | 環境から来る完了イベントの対応関係を明記。不正入力の遷移も定義 |
| S2 | Closeフレーム開始後はデータ送信を開始せず、Closeを高々一度開始する | 接続内の書き込み順序契約。失敗後のClose再試行を禁止する設計なら、その方針を明記 |
| S3 | 受付失効後の新規要求は拒否し、それを原因とするI/Oを開始しない | 失効前の受理済み要求をどうするかとは独立 |
| S4 | 発行I/O・保留Effect・完了の対応が一貫し、資源利用中は保持義務が残る | 実際に資源を保持するadapterは外部契約。モデル内のカウンタだけでUAF不在としない |
| S5 | 要求結果は高々一度確定し、遅延完了で終端状態を再開しない | operation ID・結果の意味論が必要。「必ず一度返る」は別の進行性 |
| S6 | 静止完了ではセッションの保留Effect・I/O・未解決要求がない | その状態へ到達できることは含まない。共有TCPの解放は含めない |
| R1 | 実行器の観測可能な履歴がモデルの許す履歴へ対応する | Effect生成と実行開始を対応付け、モデル外のTransport呼び出しをなくす |
| B1 | backendの履歴がsend順序・寿命保持・中断完了の契約を満たす | HTTP/1とHTTP/2で別々に根拠付ける。今回の調査では未証明 |
| L1 | 一定の環境仮定の下で、要求解決または静止完了へ進む | 公平性、タイマー、backendの完了・中断応答が必要。時間上限には定量的仮定がさらに必要 |

S群はモデルの安全性、R1は実行器との対応、B1は依存先との対応、L1は進行性である。
S群だけを証明して、利用者から見た終了保証を完成したとはしない。
HTTP/2の「当該ストリームのabortが他ストリームのcloseを直接要求しない」も候補となるが、
共有flow control・帯域・接続障害を含む完全な非干渉や公平性とは区別する。
任意のメモリや他ユーザーのデータを読めないという情報流の性質も、
ここでの終了・順序モデルの定理からは導けない。

### 8.4 空虚な安全性証明を避ける確認

全要求を拒否する、あるいは永遠に終了完了へ進まないモデルでも、
「close後に送らない」「終了完了時に保留なし」だけなら成立し得る。
正常なsend、peer Close、同時close、EOF、異常終了について、具体的に到達する履歴を作り、
要求される正常動作を許すことも確認する。
backend契約が実現可能であることをモックと実adapterで示し、
「必要な保証をそのまま外部仮定に置いただけ」の循環した根拠付けを避ける。

### 8.5 次に進める範囲

次は追加の広範な調査ではなく、**第4節と8.2の意味論を選ぶための小さな契約案**を作る。
その後、S1〜S6と正常履歴を持つ純粋モデルを試作する。
並行して、実行器が必要とする最小のbackend契約について、HTTP/1の静止・中断経路と
HTTP/2 Tunnelの実装を限定的に確認する。公開APIやbackend能力の大きな変更は、
その結果と契約の合意を得てから行う。

従って現段階は「調査不足なので何も始められない」でも「実装に必要な根拠が全部揃った」
でもなく、**条件付き安全性の設計へ進めるが、終了・資源保証には明示的なゲートを残す段階**
である。
