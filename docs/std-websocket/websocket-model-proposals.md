# WebSocket寿命管理: 三つのモデル案と比較

所属: [Std拡張WebSocket開発](./README.md)。代替案とモデル選定の記録。

2026-11-02作成。比較を経て、**Bを本体とし、Cの最小の保持不変条件を取り込む構成を
採用方針とする。純粋モデルの限定的な試作・局所補題・テストは実施済み**。
[試作結果とTransport接続条件](websocket-prototype-results.md)を参照。
本書の設計全体の実装・証明が完了したわけではない。動作原則の合意状況とHTTP整合の条件は
[動作方針](websocket-behavior-policy.md)を参照。公開API・詳細契約は未確定。
記載する型・述語は概念表記で、コンパイル確認済みのLeanコードではない。
比較時の代替案も残す。公開API・既存実装は変更しない。

前提: [問題定義・設計方針](websocket-lifetime-design.md)、
[依存先契約](websocket-dependency-contracts.md)、
[動作方針と既存慣習の調査](websocket-behavior-policy.md)。
コンベンションの参照は実装可能性を必須条件とし、Lean本体（Init・Std）を最優先、
次にws-leanと他言語の主要実装を同程度、その後に他の限定的な実装とする。
定理ID S1〜S6・R1・B1・L1は設計方針第8.3節に対応する。

## 1. 比較するもの

候補は、A「一体型の状態機械」、B「直積状態と操作台帳」、C「操作権と保持義務のモデル」。
いずれも**一つの論理セッションを単一所有タスクが駆動する**。
「actorかロックか」の比較ではなく、何を状態の中心に置いて証明するかの比較である。
単に巨大ロックを持ってrecv/sendの完了を待つ方式は、中断処理まで止めるので候補にしない。

一方、以下はモデル構造とは別に選ぶ**動作方針**である。
どの候補でも原理的には両方を記述できる。

| 論点 | 選択肢 | トレードオフ |
|---|---|---|
| ローカルclose前の受理済み未着手send | 排出する／取り消す | 排出は受理済み仕事を維持するが終了が遅れる。取消は終了を優先するが呼出側に失敗結果が必要 |
| close APIの戻り | 受付失効まで／Close書込完了まで／静止完了まで | 早期応答ほど保証が狭い。単一の成功値で混同しない |
| 実行中sendの期限到来 | 完了待ちを続ける／backend中断を要求する | 前者は終了遅延。後者も中断完了まで資源保持が必要で、能力不足なら静止を保証できない |
| 利用者への取消結果 | I/O静止後に返す／先に結果を確定する | 後者は応答性が良いが、結果確定後も内部の回収責務が残る |

これらを一度に汎用設定へする提案ではない。まず一つの契約を選び、必要がなければ
実装に設定項目を増やさない。ピアClose受信後は、ローカルclose時の排出方針にかかわらず、
未着手のアプリデータを新たに送る経路を止める方向とする。
既に実行中のフレームの完了とClose応答の順序は別途扱う。

## 2. 全案に共通する境界と語彙

### 2.1 寿命と所有の単位

- SessionはWebSocket一つ。HTTP/1では移譲された接続、HTTP/2では一つのストリームに対応する。
- Resourceはそのセッションが使用する資源。共有TCPはHTTP/2接続側の所有であり、
  セッションが解放するのは自身の参照・バッファ・ストリーム利用分である。
- アプリに渡すHandleは要求の入口だけを持つ。古いHandleの存在自体は禁止しない。
  データ配送側も同様に、所有タスクが受信した結果を渡し、生のrecv権を渡さない。
- shutdown用の制御経路はデータ要求キューの飽和で塞がれないようにする。

### 2.2 混同しない時点

```text
呼出 → キュー投入 → 所有タスクが受理 → I/O候補を予約
     → 開始を確定 → backend登録 → 完了を回収 → 結果を確定
```

キュー投入は受理ではない。受付失効前に投入されても、失効後に取り出されたsendは拒否できる。
受理前に待つ呼出も、終了時には拒否結果または明示したチャネル終了として解決する。
結果の確定と利用者への配送を分け、待機者がいなくても内部の結果を二度確定しない。

開始確定は所有タスクが行い、失効と同じ順序に置く。予約済みだが未確定の候補は撤回できる。
確定した操作は即時登録失敗も含め必ず追跡する。確定からbackend登録までを別workerへ
渡す場合には、遅れた登録を含めて追跡する追加のプロトコルが必要になる。
最初の実行器では、所有タスクが非ブロッキングの登録を行い、完了だけを非同期に待つ案を
優先して検討する。現在のAsync APIがこの分割をどう提供できるかは未検証である。

### 2.3 入出力と終了の意味

共通Eventの候補:
`Submit`、`LocalClose`、`PeerClose`、`Eof`、`Failure`、`Deadline`、
`StartFailed`、`IoCompleted`、`AbortCompleted`。
I/Oにはセッションと操作を識別するIDを付け、モデル内では単調増加するNatで再利用を避ける。
実装が固定幅IDを使うなら、枯渇時の扱いを別途定義する。

共通Effectの候補:
`PrepareWrite`、`PrepareRead`、`AbortScope`、`FinishSendDirection`、
`PublishResult`、`ReleaseOwned`。予約・開始確定・実I/Oを一つのEffectと同一視しない。
不明な完了IDや不正な遷移は明示した内部異常として扱い、正常EOFや成功にしない。
終端後にも結果確定を変えないことと、異常を観測・報告することは両立させる。

「静止完了」は、管理対象の予約・I/O・子処理・未解決要求がなくなった状態。
「正常Close交換」「送信方向の終了」「所有資源の解放確認」は別の観測値とする。
期限切れや取消結果だけで静止完了に進まない。

## 3. 案A: 一体型の状態機械

### 3.1 表現

接続全体の主要な局面を列挙型で表し、その局面で必要な情報を持たせる。

```text
Phase =
  Open
  StoppingAdmission
  SendingClose
  AwaitingPeerClose
  StoppingBackend
  Quiescent

State = Phase + Queue + WriteSlot + ReadSlot + Requests
        + CloseFacts + StopReason + OwnedResources
```

これは概念上の組合せであり、実際には各Phaseのコンストラクタへ必要なフィールドを配る。
WriteSlot/ReadSlotは予約・開始済み・完了の区別とIDを持ち、各一つまでとする。
キューやIDを含むので、状態空間全体が有限という意味での有限状態機械ではない。
ピアCloseが先に来たことはCloseFactsに記録し、局面の数を無理に増やさない。

### 3.2 主な遷移

| 現状態・入力 | 遷移・出力 |
|---|---|
| Open / send受理 | 要求を記録し、書込枠が空けば送信を予約 |
| Open / LocalCloseまたはPeerClose | 受付を失効してStoppingAdmissionへ。方針に従い未着手要求を解決 |
| StoppingAdmission / 書込枠が空く | Closeを予約・開始しSendingCloseへ。ピアClose後は新規データを開始しない |
| SendingClose / 書込成功 | ピアClose未受信ならAwaitingPeerClose、受信済みならStoppingBackendへ |
| 任意の非終端局面 / 致命的エラー | 受付失効、未着手操作の撤回、StoppingBackendへ。Closeが送れたと扱わない |
| StoppingBackend / 保留処理の回収完了 | 要求結果と所有資源の後始末を行い、条件を満たせばQuiescentへ |

AwaitingPeerCloseでも受信・期限・shutdownを処理する。
StoppingBackendは直ちに中断できたことを意味せず、能力不足ならそこに留まり得る。
Close開始履歴はphaseを進めても保持し、失敗後にCloseを再開始しない。

### 3.3 証明と評価

- S1〜S3はPhaseについての場合分けとして書きやすい。
- S4〜S6には補助フィールドの関係が必要で、Phaseだけでは足りない。
- Phase遷移をそのまま実行器の分岐に写しやすく、最初の正常履歴を確認しやすい。
- 受信・書込・Close交換・backend停止が独立に進むと、局面の追加や分岐の重複が増える。
- HTTP/2も表せるが、StoppingBackendを「TCPを閉じる」と定義してはいけない。

**適する用途**: 小さな仕様の説明・比較用の参照モデル。
機能追加のたびにPhaseが膨らむなら、補助状態へ分解する必要がある。

## 4. 案B: 直積状態 + 操作台帳

### 4.1 表現

異なる進捗を別々の軸とし、その間の不変条件を証明する。

```text
State = {
  admission : Accepting | Revoked
  closeTx   : NotStarted | Reserved id | Started id | Done outcome
  closeRx   : NotSeen | Seen details
  backend   : Active | FinishRequested | AbortRequested | Terminal outcome
  operations : OpId -> OperationRecord
  requests   : RequestId -> RequestRecord
  outbox     : List ReservedEffect
  ownedResources
}

OperationRecord = kind + scope + status + requestLink + retainedResources
status = Reserved | Started | CancelRequested | Completed outcome
```

上記の軸だけでは不正な組合せも構成できる。
例えば「closeTxがStartedなのに同時にdata writeもStarted」をS1の不変条件で排除する。
recvとwriteは並行できるが、それぞれの開始済み枠は高々一つとする。
CancelRequestedは依然として保留I/Oであり、Completedとは異なる。
完了記録をいつ捨てるか、古い通知をどう判定するかも台帳の規則に含める。

### 4.2 主な規則

1. 要求受理はadmissionとrequest台帳を更新する。
2. 送信予約はoutboxとoperationsへ同じIDを記録する。
3. 開始確定時に、予約がまだ有効か、書込枠とclose条件を再確認する。
   失効前の受理済み要求については選んだ排出方針も確認する。
4. abortは未確定予約を撤回し、開始済み操作をCancelRequestedへ移す。
   それだけではoperationsから消さない。
5. 完了はID・kindに対応する記録だけを更新する。要求結果が既に取消で確定していても、
   保持資源の回収は実施し、結果を成功へ書き換えない。
6. 静止述語は、予約・保留I/O・未解決要求・管理対象子処理が空であることから定義する。
   backendのTerminal通知だけでは、この述語を満たしたとしない。

### 4.3 証明と評価

- S2はcloseTxと書込枠、S3はadmission、S4〜S6は台帳の保存則として分けられる。
- 直積の全組合せを許すわけではないため、不変条件の設計・保存証明が中心になる。
- エラーや完了順序の入替えを、新しい大域Phaseを増やさずに記述しやすい。
- 実行器のoutbox・I/O管理と近く、R1で予約と実行の間を追える。
- 操作台帳の実装方法まで抽象モデルに持ち込むと複雑になる。
  最初はwrite/read各一枠など必要最小限にし、汎用ジョブ管理器を作らない。
- HTTP/2ではbackend scopeをstreamとし、flow-control待ちを未完了操作として表せる。
  ただしwaitの中断が実際に完了するかはB1の義務として残る。

**適する用途**: 実行可能な純粋モデルと実行器をつなぎ、寿命管理の本体にする案。

## 5. 案C: 操作権と保持義務を中心にしたモデル

### 5.1 表現

「何段階目か」より、「誰が何を開始でき、どの処理が何を保持すべきか」を中心に置く。

```text
State = {
  authority : Active generation | Revoked generation
  permits   : Set OperationPermit
  leases    : OpId -> Set ResourceId
  results   : RequestId -> Pending | Resolved outcome
  protocolFacts
}
```

Permitは開始許可、LeaseはI/O完了まで保持する義務を表すモデル上の記録。
失効前に発行したPermitも未使用なら撤回するか、受理済み排出用として残すかを契約で決める。
Leaseはアプリへ渡さず、backend登録の前に作成し、即時失敗または実完了でのみ解消する。
操作権の失効はLeaseを消さない。

Leanの通常の値は複製できるので、Permitという型を作るだけでは一回限りの使用にならない。
所有タスク内の台帳で発行・消費を検査する必要がある。
これを言語が強制する線形型、RC、RAIIと同一視しない。

### 5.2 中心となる定理

```text
開始を確定する操作には、有効かつ未消費のPermitがある
同じPermitは二度消費されない
失効後は新規要求用のPermitを発行しない
未完了operationがresourceを使うなら、そのresourceへのLeaseが残る
ReleaseOwned(resource)を出すなら、対応するLease集合が空である
```

解放にはLease空だけでなく、今後Permitを発行・行使できないこと、未実行Effectがないこと、
必要な利用者・子処理の終了も要求する。登録済みI/Oだけ数えて十分とはしない。
共有資源では「このSessionのLeaseがない」と「全SessionのLeaseがない」を区別する。

Close順序はこの所有モデルだけでは導けない。
protocolFactsとしてBのcloseTx等に相当する状態を加え、開始許可の条件に結び付ける。
S2を単に「適切なPermitだけ発行する」と仮定するのではなく、
Permit発行・消費規則から証明する。

### 5.3 証明と評価

- S3・S4の根拠が明確で、古いHandleの生存と操作権失効を直接区別できる。
- HTTP/2のSession利用権と共有接続の保持関係を表すのに向く。
- ただし共有接続の全体解放まで証明するなら、接続所有者と他ストリームのモデルも必要。
- 権利・保持の台帳とプロトコルの両方が必要で、最初から全面採用すると抽象化の負担が大きい。
- Leaseが残る定理は、実行器が実際のsocket・バッファ参照を保持する証明ではない。
  モデルのLeaseと実資源保持との対応はR1/B1で別途裏付ける。

**適する用途**: 寿命の保証を独立した補題群にし、Bの台帳を精密化する案。
最初から一般的な権限管理フレームワークを実装する提案ではない。

## 6. 同じ競合を三案で追う

比較用に「ローカルcloseで未着手sendを取消」「実行中sendは完了待ち」
「要求結果の取消はI/O静止前に確定してよい」を仮置きする。採用決定ではない。
次の履歴では、S1は開始済みsend、S2は予約済み・未着手sendを表す。

| 入力・観測 | A | B | C |
|---|---|---|---|
| S1実行中にLocalClose | StoppingAdmissionへ。S2取消、S1枠は維持 | admission失効、S2予約撤回、S1台帳は保持 | 新規Permit発行停止、S2のPermit撤回、S1のLeaseは維持 |
| 古いHandleからS3 | phaseで拒否 | admissionで拒否 | 新規Permitを発行せず拒否 |
| S1完了 | 書込枠を空けClose開始へ | S1完了を回収してClose開始条件を満たす | S1のLease解消後、プロトコル条件に従いClose用Permitを行使 |
| Close書込完了、ピア未応答 | AwaitingPeerClose | closeTxはDone、closeRxはNotSeen | Close用Leaseは解消。protocolFacts上はピア応答待ち |
| 期限到来 | StoppingBackendへ。recv枠が残れば静止でない | AbortRequested。未完了recvは台帳に残る | recv用Leaseが残る限り対象資源を解放しない |
| backendが中断を完了できない | 静止完了へ進まない | 同左 | 同左 |

「Closeの後もrecvが保留」「利用者には取消済みだがnative I/Oは保留」という状態を、
Aは局面と付帯情報、Bは独立軸、Cは権利と保持義務の違いで説明する。
どの表現も、期限切れから静止完了を捏造しない。

追加で全案に必要な履歴は、PeerCloseが先行、同時close、Close送信失敗、
EOFとキャンセルの区別、abort前の予約の遅延実行、重複完了、キュー飽和、
HTTP/2送信credit待ちと共有接続障害である。
これらと正常なsend・Close交換の到達例を、sleepに依存しない入力列で確認する。

## 7. 違いのまとめと推奨

| 比較軸 | A: 一体型 | B: 直積・台帳 | C: 操作権・保持義務 |
|---|---|---|---|
| 説明の中心 | 接続はいまどの局面か | 各進捗と未完了操作は何か | 何を開始でき、何を保持すべきか |
| 初期の記述量 | 比較的少ない | 中程度 | 多い |
| 証明の中心 | 局面ごとの場合分け | 軸間の不変条件・操作の対応 | 発行・消費・保持の保存則 |
| 完了順序の入替え | 分岐が増えやすい | 自然に表しやすい | 保持は自然。プロトコル状態は別途必要 |
| 実行器との距離 | 単純な段階では近い | 予約・開始・回収と対応させやすい | 実際の参照保持との対応付けが重い |
| HTTP/2の共有寿命 | 表現可能だが付帯情報が増える | stream scopeで分離しやすい | 共有・非共有の保持義務を明記しやすい |
| 主な危険 | Phaseだけで寿命を説明したつもりになる | 台帳を過度に汎用化する | 型やLeaseだけでnative安全性を証明したつもりになる |

**Bを本体とし、Cから寿命に必要な最小の保持不変条件を取り込む構成を採用方針とする**。
プロトコルの見通しにはAの局面図を使えるが、AとBを二つの正として別実装しない。
Aを正式な抽象仕様として残す場合は、Bの履歴をAへ写す対応関係を別に定義する必要がある。
必要性がなければAは説明用に留める。

この組合せは、既存設計の「単一所有タスク・非同期I/O追跡」を維持しつつ、
寿命の問題をCloseフラグだけで説明しないためのもの。
ただし三案間の精緻化関係や同等性を証明済みという意味ではない。

## 8. 選択後の最小作業と未保証範囲

1. [既存慣習の調査](websocket-behavior-policy.md)を踏まえて、第1節の動作方針、
   結果型、静止と解放の観測方法を合意する。
2. 採用するBは、write/read各一枠、要求キュー、未実行予約、Close事実だけで始める。
   close後に残る利用者向け受信データの配送・破棄方針と保持量も決める。
3. S1〜S6を分割して定式化し、正常・異常の具体的な到達履歴を同時に作る。
4. 実行器の開始確定とbackend登録をどう対応させるかを検証する。
   開始・中断・完了の即時失敗もモックで再現し、R1に必要な対応関係を記録する。
5. HTTP/1とHTTP/2についてB1を個別に確認する。中断能力が不足する場合は、
   「受付失効と保持の安全性は保証するが、静止への到達は未保証」と明示する。

どの案もnative全体のメモリ安全性や情報漏洩不在、無条件の有界資源回収を保証しない。
L1は環境の公平性・backendの完了能力を前提とする別定理である。
候補の選択は、その外部仮定を消すことではなく、**仮定と実装上の義務を見える形にする**
ために行う。
